# UI Foundation and Visual Maintenance

This document records the current visual foundation after the migration to
Tailwind CSS and shadcn/ui. Follow these rules to keep the MVP simple, useful,
and centered on the map.

## Current Foundation

- The project uses Tailwind CSS 4 with tokens defined in `src/index.css`.
- The project uses shadcn/ui v4 with components copied into the codebase.
- The current shadcn/ui primitive is Base UI, provided by the
  `@base-ui/react` dependency.
- The shadcn configuration is stored in `components.json` at the project root.
- UI components are stored in `src/components/ui/`.
- The `cn()` utility is stored in `src/lib/utils.ts`.
- Internal imports may use the `@/*` alias configured in `components.json`.

Currently available shadcn/ui components:

```text
src/components/ui/
  accordion.tsx
  badge.tsx
  button.tsx
  checkbox.tsx
  input.tsx
  scroll-area.tsx
  separator.tsx
  sheet.tsx
  tooltip.tsx
```

Supporting variant files, such as `button-variants.ts` and
`badge-variants.ts`, are also part of the local UI foundation.

## Adding shadcn/ui Components

Add components only when the interface has a real need for them. shadcn/ui
copies code into `src/components/ui/`, so each new component becomes code
maintained by the project.

Recommended workflow:

1. Confirm that the component addresses an MVP need.
2. Use the shadcn CLI to add the required component.
3. Do not run `shadcn init` without a reason: the project already has
   `components.json`, `src/index.css`, `src/components/ui/`, and
   `src/lib/utils.ts` configured.
4. Avoid `add --all`; add only the component that will be used.
5. Review the diffs generated by the CLI, including dependencies, imports, and
   tokens.
6. Run the validation checks before considering the change complete.

Example:

```bash
pnpm dlx shadcn@latest add dialog
pnpm lint
pnpm build
```

When you need to inspect a component before installing it, prefer CLI commands
such as `docs`, `view`, or `--dry-run`.

## Visual Conventions

- The map is always the first experience. Do not replace the initial screen
  with a landing page or product introduction.
- On desktop, keep the sidebar with search, filters, and results; the map must
  occupy the remaining space.
- On mobile, keep the map as the main screen, search at the top, and filters in
  a `Sheet`.
- Avoid excessive decorative cards. Use cards only when they help organize
  repeated items, empty states, or details.
- Prefer a functional, dense, and clear UI. Users should find NPCs, enemies,
  areas, and resources with only a few clicks.
- Use theme tokens (`bg-background`, `text-foreground`, `border-border`,
  `bg-card`, `text-muted-foreground`, `ring-ring`) instead of ad hoc colors.
- Use specific colors only when they communicate map data. Marker colors come
  from the area registered in `src/data/areas.json`; a warp point uses an extra
  ring or border without changing the area's base color.
- Do not add large visual effects, decorative gradients, or permanent blocks of
  text over the map without a clear need.

## Scrolling Conventions

- Use `ScrollArea` for internal app panels with a constrained or fixed height,
  such as result lists and filter options in the sidebar. This keeps the
  scrollbar visually consistent and contains the gesture within the panel.
- Prefer native page or parent-container scrolling when content should grow
  naturally with the layout without creating a second scroll area.
- Use `overflow-*` directly only for structural containers, integrations with
  external libraries, or cases where the app primitive interferes with the
  expected native behavior.
- Leaflet popups continue to use Leaflet's own height limit and native overflow.
  The library uses those measurements to position and automatically adjust the
  popup on the map, so wrapping its content in another `ScrollArea` can impair
  auto-pan, touch input, and nested scrolling.

## Marker Popup Monster Drops

The MarkerPopup displays each monster as a distinct compact row in the Monsters
section. A monster with drops shows its thumbnail and linked name when
available, its exact drop count, and a sibling accordion button. Drop panels
are collapsed by default and expand independently beneath their owning monster.
Monsters without drops remain compact rows and do not receive an accordion
control.

Expanded panels use a compact vertical list with the drop name on the left and
its exact percentage aligned on the right. An optional `wikiSlug` makes the name
a wiki link, and an optional `image` adds a thumbnail. When `image` is missing
or exactly empty, the popup omits the image element so it does not produce a
broken thumbnail or an empty placeholder.

Accordion buttons expose `aria-expanded`, identify the corresponding panel,
and have an accessible label containing the monster name and drop count. The
monster wiki link and accordion button remain sibling controls so an anchor is
never nested inside a button. Every drop list is named `Drops from
${monster.name}`. Visible keyboard focus must remain clear in light and dark
themes.

Keep popup overflow under Leaflet's native height limit and scrolling behavior.
Do not introduce a nested `ScrollArea` for monster drops.

When verifying popup changes on desktop and mobile:

- open a marker containing monsters with and without drops;
- confirm every monster drop panel starts collapsed and controls expand
  independently with mouse, touch, Enter, and Space;
- confirm every drop remains grouped beneath the correct monster;
- confirm names, exact percentages, optional wiki links, and known images
  render correctly;
- confirm missing and empty images render without a broken image or gap;
- use enough content to trigger overflow and confirm Leaflet's native popup
  scrolling, map auto-pan, mouse-wheel behavior, and touch scrolling still work.

## Global CSS

`src/index.css` must remain lean and contain only:

- Tailwind, shadcn/ui, animation, and font imports;
- theme tokens and `@theme inline`;
- `@layer base`;
- essential styles for Leaflet, the map container, and markers.

Prefer Tailwind classes in components for layout, spacing, typography, borders,
states, and responsiveness. Avoid recreating large blocks of handwritten CSS or
adding global selectors for cases that can live in the component.

## UI Change Checklist

Before completing a visual change:

- Run `pnpm lint`.
- Run `pnpm build`.
- Test the desktop layout with the sidebar, search, filters, and results.
- Test the mobile layout with the main map, search at the top, and filters in
  the `Sheet`.
- Confirm that search and filters work together.
- Click a search result and confirm that the map centers on its marker.
- Click a marker and confirm that its popup opens.
- Add or adjust a marker through JSON and confirm that no code change is needed.
- Confirm that the change does not add a backend, login, an admin panel,
  comments, favorites, clustering, Fuse.js, automatic routes, public
  collaboration, or wiki synchronization.
